0. TL;DR — What's in here now

Shipped

  • Customer booking flow writes to DB, returns a real reference, sends confirmation email (Resend), shows the booking with a cancel link.
  • Admin dashboard at /admin.html (Linear-style): list, day view, week view, customer drawer, status changes, command palette (⌘K), keyboard shortcuts.

Assumptions you should confirm

  • Hermes contract. I assumed Hermes is the user's existing Hermes Agent system (~/.hermes/) and the integration point is: LUCA exposes past-client + booking data to Hermes, and Hermes posts back reactivation activity (sends, opens, replies, recovered bookings). If Hermes here means something else (e.g. a specific named agent profile), the contract still holds — just plug it into a single agent record. See §6.
  • Availability is heuristic. Real-life calendar/staff constraints aren't modelled (no resources, no employees, no double-booking enforcement beyond an exclusion index on overlapping bookings for the same service). LUCA probably needs more granular resource modelling before a hard cutover. See §4.
  • Payments are out of scope. The flow records a booking and emails a confirmation. No money is taken. Adding Mollie or Stripe is a clean swap-in but explicitly deferred. See §10.
  • CSV column shapes. Past-client importer assumes a permissive schema: any of email, e-mail, e_mail → email; first name, voornaam, firstname → first name; etc. Mapping is shown in the preview step so admins can correct it.
  • Admin invites. First admin is created manually via SQL after Supabase auth signup (see README). No self-service invite UI yet.

1. Stack & architecture

Database — Supabase (Postgres)

Picked Supabase because: hosted Postgres, built-in row-level security, free auth, free storage, and one less moving piece on a Netlify-first site. The alternative was Netlify Blobs or a separate Render/Fly Postgres — both add operational surface for a small win.

Schema lives in db/schema.sql, seed in db/seed.sql. Migration files under db/migrations/ are timestamp-prefixed and idempotent. See §3 for the schema.

Backend — Netlify Functions (Node 22)

The customer-side site must never see the Supabase service role key, so all writes that bypass RLS go through Netlify Functions. The admin dashboard signs in via Supabase Auth and uses the anon client + RLS for everything it does — same Postgres, but the JWT establishes who's calling.

Function code in netlify/functions/. Shared helpers in netlify/functions/_shared/. Deploy is automatic on Netlify push.

Email — Resend

Single transactional sender, simple SDK, native Netlify Function support. Templates are inline HTML strings (NL + EN) — not worth pulling in MJML for two emails. From address defaults to LUCA Amsterdam <reserveringen@luca-amsterdam.nl>; override via LUCA_FROM_EMAIL env. For local/preview, if no RESEND_API_KEY is set the function logs the email payload and pretends to succeed — keeps the flow demoable without keys.

Frontend — kept the existing pattern

Customer site stays vanilla HTML + React 18 via UMD CDN + Babel-compiled JSX. I considered Vite, but the cost of introducing a bundler (build step, source maps, CI, deploy contract changes) for what is still mostly static pages is not worth it. The existing booking flow is a single React app island; the admin is a second island on its own page. Both share React via UMD.

Build step: still npx babel. Added an npm run build that compiles all .jsx sources to .js. Netlify build command runs this so deploys always serve fresh JS.

Auth model

Two-tier:

  • Customer: no account, ever. Just email + name in the booking form. The cancel link in the confirmation email contains a one-time token bound to that booking.
  • Admin: Supabase Auth (email + password). Row in admin_profiles assigns role. RLS policies block everything for anon; allow read/write for any authenticated user with a row in admin_profiles.

4. Booking + availability

Submit path

  1. Customer fills the 5-step flow (unchanged UX).
  2. On confirm, frontend POSTs to /.netlify/functions/create-booking with the booking payload.
  3. Function validates → upserts customer by email → inserts booking → returns { reference, cancel_url }.
  4. Function fires confirmation email (NL/EN based on language) via Resend.
  5. Frontend lands on the confirmation screen showing the real reference, and clears local-storage state.

Availability: heuristic, not authoritative

The original calendar used a hash-of-date to fake availability. I replaced this with a real query that:

  • Counts existing bookings overlapping each slot for the requested service category.
  • Blocks the slot if a configurable per-service capacity is exceeded.
  • Falls back to "available" if capacity isn't set (early days — better to overbook than to block real customers).

The capacity model is a single integer per service, not per resource. Real wellness booking needs staff/room modelling — defer until LUCA tells us their real constraints.

Confirmation email

Plain-text + HTML, NL or EN based on customer language. Contains: reference code, service + duration, date/time (formatted in customer language), address, cancel link. The cancel link points to /cancel.html?ref=…&token=… — both the reference and a per-booking token are required, so leaked links can't cancel arbitrary bookings.

5. Admin dashboard

Linear-style — what that means here

  • Dense, calm, fast. 14px base font, tight rows, no purely decorative chrome.
  • Keyboard-driven. ⌘K command palette. g b bookings, g c customers, g s schedule, g i import, g h hermes. j/k to move in the list. e edit. x archive/cancel. ? shortcut help.
  • Optimistic UI. Status changes show the new state instantly and roll back on failure.
  • Dark mode by default, with toggle for light. Matches the operator-tool feel.

6. Past-client import

Three-step flow

  1. Upload. Drag a CSV. Parsed in-browser to detect columns + show row count.
  2. Preview. Each detected column maps to a customer field (auto-guess, manually correctable). We POST the parsed rows + mapping to /import-preview which returns: rows to insert, duplicates (matched on email or phone), invalid rows (no email + no phone), and any conflicts.
  3. Commit. POST to /import-commit with the same import_job_id. Inserts new customers with source='import', tags them with imported-YYYY-MM-DD, optionally adds a custom tag for the batch. Returns final counts.

Dedupe contract

A row is a duplicate if either email or phone matches an existing customer. Email match wins (canonical), phone is fallback. Imported rows never overwrite — they're listed in the preview as "duplicates" and skipped on commit.

7. Hermes integration

What I assumed Hermes means here

An external automation agent (likely the user's own Hermes Agent in ~/.hermes/) that:

  • Reads past clients from LUCA to run reactivation campaigns (email, SMS, whatever).
  • Posts back what it did so an admin can see in one place: agent X sent a campaign to N customers, M replied, K rebooked.

If "Hermes" here means a different specific thing, the same contract still works — it's just an authenticated outbound + inbound API. The agent record is a single row; multiple agents can coexist.

API contract

Both endpoints require Authorization: Bearer <api_key>. The key is shown once at creation; only its SHA-256 hash is stored. last_seen_at updates on every call.

GET /.netlify/functions/hermes-past-clients
    ?since=2025-01-01     # optional, last_seen_at > this
    &tag=imported-2025-05 # optional, customer has this tag
    &limit=500            # default 200, max 1000
→ { customers: [{ id, email, full_name, phone, language, tags, last_seen_at }] }

POST /.netlify/functions/hermes-activity
Body: { kind, customer_id?, customer_email?, payload? }
→ { id, created_at }

Loud assumption

I'm not spawning a Hermes agent process inside this repo. Hermes lives elsewhere (the user's machine). This integration gives Hermes a stable contract to talk to LUCA. If you wanted LUCA to actually trigger Hermes outbound from the admin UI (e.g. "run a reactivation campaign on these 200 customers"), that's a different feature — add a "trigger campaign" endpoint that Hermes polls or webhooks. Mark this as deferred unless you say otherwise.

10. Open questions / deferred

  • Payments. Mollie (Dutch-first) or Stripe? Should the booking be "pending until paid" or pay-on-arrival like the existing OnlineAfspraken setup?
  • Real availability. Need staff + room modelling. How many massage therapists? How many sauna rooms? Conflicts per resource, not per service.
  • OnlineAfspraken backfill. Should existing OA bookings sync into this DB so the admin sees one calendar, or do we cut over fully?
  • Admin invite UI. Right now first admin is created via SQL. A self-service "invite teammate" flow is one Netlify function away.
  • SMS confirmations. Twilio/MessageBird. Likely a "nice-to-have" once Resend email is humming.
  • Hermes outbound trigger. If admins should kick off Hermes campaigns from the UI, need a trigger endpoint + agent-side webhook handler.
  • Custom domain. Production should live on book.luca-amsterdam.nl or similar; right now the URL is the Netlify subdomain.
  • Backups. Supabase has nightly backups on paid plans. Free tier does not — confirm we're on a plan with backups before going live.
